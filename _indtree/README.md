# `_indtree` — 煤电 + 工业联合减排的求解树（v9 管网）

建于 2026-09-09。存在的唯一理由：**仓库根 `inputs/` 的候选管网够不着 38% 的封存汇，
工业侧的任何结论都会被这个缺陷决定，而不是被物理决定。**

---

## 一、为什么必须另起一棵树

在仓库根（v7 输入版）上跑完四个 `IND_*` 情景后，`_t95` 一对在 2060 年出现
**286.7–290.1 Mt/yr 的注入能力松弛**——模型宁可付 5×10⁹ 元/Mt 的 big-M，也不把 CO₂ 送去别的汇。
查网络本身，原因不是空间经济性，是**图断了**：

| | 仓库根 `inputs/`（v7） | `_v9tree/inputs/`（v9） |
|---|---|---|
| 基础节点 / 候选边 / 汇 | 612 / 923 / 35 | 666 / 2 651 / 89 |
| 连通分量 | 64，最大占 77.8% | 54，最大占 89.6% |
| **汇在最大分量内** | **26 / 35** | **89 / 89** |

求解器实际用的运行时网络（含煤电 350 + 工业 390 条支线）更糟：

| | 仓库根（v7 网络） | **本树（v9 网络）** |
|---|---|---|
| 运行时节点 / 边 | 1 002 / 1 313 | 1 056 / 3 041 |
| 连通分量 / 最大分量占比 | 64 / 79.4% | 54 / **90.9%** |
| 汇在主分量内 | 26 / 35 | **89 / 89** |
| **可达注入能力** | **794.4** Mt/yr | **1 282.6** Mt/yr（全部） |
| 煤电厂址在主分量 | 312 / 350 | **350 / 350** |
| 工业厂址在主分量 | 320 / 390 | 363 / 390 |

其中 **S002 在 v7 里是孤立节点（度 = 0）**，200 Mt/yr 的注入能力永远用不到。
v7 求解里"扣掉越限量后的注入 811.8 Mt/yr"几乎正好等于"可达能力 794.4 Mt/yr"——
松弛量就是**够不着的那部分**，不是"中国的汇装不下"。

CLAUDE.md §二.6 记的 "v8 = 重建版本（103 个汇、**连通性修复网络**）" 说的就是这个缺陷。

### v9 网络上仍然剩下的缺陷（已量化，是有界的）

不是全好了，剩下的部分必须一起报出来：

| | |
|---|---|
| 工业厂址在主分量外 | **27 / 390**，排放 **160.3 Mt（占工业 4.9%）** |
| 其中所在分量内有汇的 | **0 个** — 这 27 个厂址一旦选 CCS，必付 big-M |
| 主分量内、汇可达的工业排放 | **3 108.9 / 3 269.2 Mt（95.1%）** |

分行业：水泥 13 个 31.9 Mt、钢铁长流程 5 个 37.1 Mt、甲醇 3 个 65.7 Mt、
合成氨 3 个 12.5 Mt、电炉钢 3 个 13.1 Mt。煤电厂址 **350/350 全部可达**。

对比 v7 的 38% 注入能力不可达，这已经是可接受的余量；但**只要 `slack_detail.csv` 里
出现注入能力松弛，先核对是不是这 27 个厂址造成的**，再谈物理解释。

## 二、这棵树是怎么拼的

`inputs/` 是仓库根 `inputs/` 的完整副本，**只替换三个网络文件**：

```
pipeline_nodes.csv            612 -> 666     取自 _v9tree/inputs/
pipeline_candidate_edges.csv  923 -> 2651    取自 _v9tree/inputs/
storage_hubs.csv               35 -> 89      取自 _v9tree/inputs/
```

其余一律不动：`plants.csv`、`industry_hubs.csv`、`industry_sources.csv`、
`water_availability.csv`、`water_nodes.csv`、`water_basin_caps.csv`、
生物质与氨的供给曲线和连接表。

### 为什么这不算跨版本混用（CLAUDE.md §二.6）

逐列实测过，不是推断：

* 仓库根 `plants.csv` 是 `_v9tree/inputs/plants.csv` 的**严格超集**——同样 350 个 `plant_id`、
  同样顺序，32 个共有列的数值差全部 < 1e-9，只多 4 个 v9.1 需要的取水强度列
  （`once_through_withdrawal_*`、`air_withdrawal_*`）。
* v9 的 `pipeline_nodes.csv` 引用的 350 个 `plant_id` **全部存在**于 `plants.csv`。
* `water_availability.csv` 与 `water_nodes.csv` 与 `_v9tree` 逐字节相同（v9.1 已核对）。
* `water_basin_caps.csv` 由指标、预留、`plants.csv` 与 `industry_sources.csv` 生成，
  **不含任何管网信息**，所以直接沿用是正确的。

换句话说：被换掉的是**管网与汇**，被保留的是**源与水**，两者在输入侧没有交叉依赖。

`data/` 是指向仓库根 `data/` 的 junction（流域矢量、封存汇栅格等只读大文件）。

## 三、跑什么

```bash
cd _indtree
python scripts/run_single.py IND_BASE_t95                 --threads 8   # 无水约束，目标咬住
python scripts/run_single.py IND_WA_cwatm_126_dry_oq_t95  --threads 8   # + 官方指标流域上限
python scripts/run_single.py IND_BASE                     --threads 8   # 目标不咬的对照
python scripts/run_single.py IND_WA_cwatm_126_dry_oq      --threads 8
python scripts/summarize_industry_runs.py IND_BASE_t95 IND_WA_cwatm_126_dry_oq_t95
```

线程固定 8，MIPGap 1%，最多 2 路并发（CLAUDE.md §二.1/2/5）。

### 求解状态（2026-09-09）

| 情景 | 末年联合份额 | 状态 | 目标函数 | gap | 用时 |
|---|---|---|---|---|---|
| `IND_BASE_t95` | 0.95 | ✅ | 1.352249e13 | 0.98% | 5 232 s |
| `IND_WA_cwatm_126_dry_oq_t95` | 0.95 | ✅ | 1.501415e13 | 0.94% | 2 074 s |
| `IND_BASE` | 0.5914 | ✅ | 1.290167e13 | 1.00% | 7 574 s |
| `IND_WA_cwatm_126_dry_oq` | 0.5914 | ✅ | 1.447115e13 | 0.99% | 12 821 s |

**目标开始咬住的阈值 f\* = 0.725。** `IND_BASE` 的 2060 年煤电一家就减 6 277.0 Mt，
比 0.5914 要求的 5 122.4 Mt 富余 1 154.6 Mt，工业一动不动——所以 0.5914 那一对里
"工业不减排"是目标水平的产物，不是工业的性质。

**缺陷确认已修复**：`IND_WA_..._oq_t95` 的注入能力松弛从 v7 的 290.1 Mt/yr 降到 **0**；
2060 年注入 1 281.6 / 能力 1 282.6（99.9%），81/89 个汇在用。
代价是 v7 那一轮把工业的角色高估了约 11%（工业减排 1 879.0 → 1 687.2 Mt）。
（2026-09-10 更正：此前写的"11 段管道容量松弛共 1.5 Mtpa"是误读——那 11 段是流量大于零而
建成容量为零的边，即 big-M 容量松弛，已由 I14/I15 的整数管径档位堵住，见下。）

### `ST_` 系（2026-09-10 起：部门碳目标，零碳价）

`IND_` 系之后的重构（部门目标、利用小时轨迹、工业产量指数、封存爬坡、整数管径、全国生物质 / 氨 / 氢上限、
capex 与走廊参数改出处值）见 `docs/工业联合减排实现说明.md` §九。**`ST_` 与 `IND_` 不得相减。**

求解流程固定为三步（§9.7）：LP 松弛写 `.sol` → 由 `.sol` 给整数变量设 MIP start → 正常 MIP：

```bash
S=<ASCII 路径>/ST_BASE_lp.sol
COAL_RETROFIT_LP_RELAX=1 COAL_RETROFIT_WRITE_SOL=$S python scripts/run_single.py ST_BASE --threads 8 --time-limit 1800
COAL_RETROFIT_START_SOL=$S COAL_RETROFIT_LOG_INCUMBENTS=1 python scripts/run_single.py ST_BASE --threads 8
```

| 情景 | 模型 | 状态 | 目标函数 | gap | 用时 | 备注 |
|---|---|---|---|---|---|---|
| `ST_BASE_inthub` | hub 决策整数 | ⏱ 时限 | 4.008e12 | 4.22% | 36 256 s | 下界停在根 LP 3.839e12；四年缺口全零；**只作参照** |
| `ST_WA_cwatm_126_dry_oq_inthub` | hub 决策整数 | ⏱ 时限 | 5.124e12 | 12.1% | 36 201 s | 2040 水泥缺口 0.1 Mt；**只作参照** |
| `ST_BASE` | hub 决策连续（§9.8） | ✅ gap 3% | 3.896233e12 | 2.99%（下界 3.7798e12） | 1 302 s | 四年缺口与物理松弛全零；1% 版跑 2 h 停在 3 896 / 3 781，日志 `ST_BASE_gap1_partial.log` |
| `ST_WA_cwatm_126_dry_oq` | hub 决策连续 | ✅ gap 3% | 4.570460e12 | 2.99%（下界 4.4338e12） | 303 s | 缺口全零；K 流域 2030 年超指标 0.74 亿 m³、2040 年 0.013 亿 m³（I21，结构性，作者决定不动），罚项 0.41e12 计入目标 |

**`ST_` 系 MIPGap 统一 3%**（作者决定 2026-09-11，CLAUDE.md §二.2 例外条款）：剩余 gap 是整数管径的固有间隙，
差值只能按可证区间报告。1% 版停摆时的水约束目标函数差：下限 (4 445 − 3 896)/3 896 = 14.1%，
上限 (4 570 − 3 781)/3 781 = 20.9%。
**3% 版定稿区间**：下限 (4 433.8 − 3 896.2)/3 896.2 = **13.8%**，上限 (4 570.5 − 3 779.8)/3 779.8 = **20.9%**，
即水约束把目标函数抬高 13.8–20.9%（含 K 流域罚项 0.41e12；扣掉罚项后下限约 3.2%——罚项是否算成本由作者定）。
两个运行都在 2050 年把注入能力用满（1 020 / 1 026 与 1 026 / 1 026 Mtpa）、生物质用满 16 EJ；掺氨在两个情景里均为 0。
空冷改造（容量加权）：BASE 2030 年 11.0%，WA 19.0%——水约束在 2030 年多推 8 个百分点空冷。

裸 MIP（无热启动）的可行解在 80 min 内始终带 250–300 Mt 水泥缺口、gap 42–45%；
LP 松弛能用水泥 CCS 满足全部上限，所以热启动是必需的，不是加速。
`*_lprelax.log`、`*_lp.sol`、`*_inthub.log` 都在 `logs/`。

## 四、纪律

1. **本树的运行不得与仓库根 `results/IND_*` 相减。** 那批用的是 v7 管网，可达注入能力只有本树的 62%。
   根目录那四个运行的价值仅限于**接线验证**（工业是否正确进入管网、流域约束与联合目标），
   其**捕集量、注入分布、工业通路份额一律不可引用**。
2. **同样不得与 `_v91tree/` 或任何非 `IND_` 运行相减。** 目标函数分母（5 392 → 8 661 Mt）、
   约束与源群三者同时变了。
3. 本树的两对情景之间（`IND_BASE_t95` ↔ `IND_WA_..._oq_t95`）**可以相减**：同一模型、
   同一目标，只差 `apply_basin_cap` 一个旋钮。
4. 引用任何成本差之前先看 `slack_detail.csv`：只要有 big-M 松弛，差值里就混着罚参数而不是价格。

实现、参数出处与已知偏差：`docs/工业联合减排实现说明.md`（仓库根）。
