# `_indtree` — 煤电 + 工业联合减排的求解树（v9.2 管网，2026-09-12 重建）

建于 2026-09-09。存在的唯一理由：**仓库根 `inputs/` 的候选管网够不着 38% 的封存汇，
工业侧的任何结论都会被这个缺陷决定，而不是被物理决定。**

---

## 一、为什么必须另起一棵树

在仓库根（v7 输入版）上跑完四个 `IND_*` 情景后，`_t95` 一对在 2060 年出现
**286.7–290.1 Mt/yr 的注入能力松弛**——模型宁可付 5×10⁹ 元/Mt 的 big-M，也不把 CO₂ 送去别的汇。
查网络本身，原因不是空间经济性，是**图断了**：

| | 仓库根 `inputs/`（v7） | `_v9tree/inputs/`（v9） |
|---|---|---|
| 基础节点 / 候选边 / 汇 | 612 / 923 / 35 | 666 / 2 651 / 89 |
| 连通分量 | 64，最大占 77.8% | 54，最大占 89.6% |
| **汇在最大分量内** | **26 / 35** | **89 / 89** |

求解器实际用的运行时网络（含煤电 350 + 工业 390 条支线）更糟：

| | 仓库根（v7 网络） | **本树（v9 网络）** |
|---|---|---|
| 运行时节点 / 边 | 1 002 / 1 313 | 1 056 / 3 041 |
| 连通分量 / 最大分量占比 | 64 / 79.4% | 54 / **90.9%** |
| 汇在主分量内 | 26 / 35 | **89 / 89** |
| **可达注入能力** | **794.4** Mt/yr | **1 282.6** Mt/yr（全部） |
| 煤电厂址在主分量 | 312 / 350 | **350 / 350** |
| 工业厂址在主分量 | 320 / 390 | 363 / 390 |

其中 **S002 在 v7 里是孤立节点（度 = 0）**，200 Mt/yr 的注入能力永远用不到。
v7 求解里"扣掉越限量后的注入 811.8 Mt/yr"几乎正好等于"可达能力 794.4 Mt/yr"——
松弛量就是**够不着的那部分**，不是"中国的汇装不下"。

CLAUDE.md §二.6 记的 "v8 = 重建版本（103 个汇、**连通性修复网络**）" 说的就是这个缺陷。

### v9 网络上仍然剩下的缺陷（已量化，是有界的）

不是全好了，剩下的部分必须一起报出来：

| | |
|---|---|
| 工业厂址在主分量外 | **27 / 390**，排放 **160.3 Mt（占工业 4.9%）** |
| 其中所在分量内有汇的 | **0 个** — 这 27 个厂址一旦选 CCS，必付 big-M |
| 主分量内、汇可达的工业排放 | **3 108.9 / 3 269.2 Mt（95.1%）** |

分行业：水泥 13 个 31.9 Mt、钢铁长流程 5 个 37.1 Mt、甲醇 3 个 65.7 Mt、
合成氨 3 个 12.5 Mt、电炉钢 3 个 13.1 Mt。煤电厂址 **350/350 全部可达**。

对比 v7 的 38% 注入能力不可达，这已经是可接受的余量；但**只要 `slack_detail.csv` 里
出现注入能力松弛，先核对是不是这 27 个厂址造成的**，再谈物理解释。

### 2026-09-12：备选管网重建（上面那张缺陷表已作废）

原网络里工业点源根本不在节点表中，求解时才临时挂上去，并给每个点源补 5 条到最近汇的
直连弧（`runtime_direct_fallback`）。这些弧是在去交叉**之后**追加的，所以以直线横穿整张
图——2050 年它们承担了 41 575 km、930 Mt，占管网长度的一半。图上那些"很奇怪的线"就是它们。

重建后的规则（`builders/network.py`、`builders/network_branches.py`）：

1. 工业点源与煤电、封存汇一起进入节点表，一起做 Delaunay 三角剖分；
2. 西藏不参与减排：点源在装载时剔除（4 个水泥点源），穿越西藏的新建候选边一律删除；
3. 去交叉的优先级仍是"既有管廊 > 接入支线 > 三角剖分"，但同优先级内改为**短边优先**
   （原来按建表顺序，长边先占位会把一整片短边挤掉：保留边 1 224 → 1 269）；
4. 连通性修复不再回填"当初因相交被删的边"（回填等于把交叉放回图上，实测 136 条、
   62 处交叉），改为在缺汇片区与含汇片区之间**新增一条不与任何保留边相交的最短连线**；
5. **片区合并**：只保证"每个源能到某个汇"是不够的。去交叉把图切成 45 片之后，南海那个
   200 Mtpa 的离岸汇 S002 落在 35 节点的小片里，全国只有 28 个源够得着它——`IND_*_t95`
   的 2060 年因此有 26 个小汇被超注入 196 Mt/yr，而 S002 闲置 162 Mt/yr。备选网络不该替
   优化器决定"谁不许去哪个汇"，所以逐次补一条最短、不交叉、不过西藏的连线把片区并成一张
   网（45 条，中位 10.5 km，最长 837 km 即那条跨海连线）；建不建仍由优化器决定。
6. 源汇专线（每个源到最近 5 个汇，2.8 倍造价）保留这一真实选项，但逐条做相交检验，
   穿过管网的直接丢弃：3 680 条候选只留下 135 条。

| | 原网络 | 重建后 |
|---|---|---|
| 节点 / 边 | 666 / 2 651 | **1 052 / 1 559** |
| 工业点源在节点表中 | 否 | **是（386 个）** |
| 源到汇不可达 | 工业 27 个 | **0（736 个源全部可达）** |
| 每个源可选的汇 | — | **89 个，即全部** |
| 新建线之间的交叉 | 62 处 | **0 处** |
| 全图残留交叉 | — | **2 处**（缝合线与既有燃气管廊，为保连通不得不留） |

（剩下 2 个连通片：一个含全部源与全部汇，另一个是西藏一侧的孤立管廊碎片，
不含任何源或汇——它的合并连线穿过西藏，按规则被删掉了。）

优化侧同步剔除西藏点源（`optimization/industry.py`）：部门碳目标是各组自身 2030 基线的
比例，基线随点源集合一起缩放，因此剔除既不放松也不收紧目标。运行期不再新建
`industry::` 临时节点，直接复用节点表里的 `industry_hub` 节点。

**因此 `ST_` 系必须整族重解，重解前的结果一律作废。**

## 二、这棵树是怎么拼的

代码只有仓库根 `src/` 一份（2026-09-22 起）。`scripts/_bootstrap.py` 里 `ROOT` 是本树根
（`ProjectPaths(ROOT)` 读本树 `inputs/`、写本树 `results/`），`SRC` 指向仓库根 `src/`。
**`ROOT` 不能改成仓库根**：那样本树的求解会悄悄改读仓库根的 v7 输入（35 汇 / 923 边、无工业节点）。
万一读错，`build_runtime_network` 会因"有源到不了任何汇"直接报错。

`inputs/` 是仓库根 `inputs/` 的完整副本，**只替换三个网络文件**：

```
pipeline_nodes.csv            612 -> 1052    2026-09-12 重建（此前 666，取自 _v9tree/inputs/）
pipeline_candidate_edges.csv  923 -> 1559    2026-09-12 重建（此前 2651，取自 _v9tree/inputs/）
storage_hubs.csv               35 -> 89      取自 _v9tree/inputs/
```

> ⚠ 截至 2026-09-22，本目录只有 `sector_targets_times_cn60.csv` 与 `industry_output_index_times_cn60.csv`
> 两个文件入了库，重建后的管网等其余输入只在作者本机。它们是 `ST_` 系重解的前提，应一并入库。
> `ST_CP_BASE` 还需要 `sector_targets_none.csv`（ba967c1 只加到了仓库根 `inputs/`）。

其余一律不动：`plants.csv`、`industry_hubs.csv`、`industry_sources.csv`、
`water_availability.csv`、`water_nodes.csv`、`water_basin_caps.csv`、
生物质与氨的供给曲线和连接表。

### 为什么这不算跨版本混用（CLAUDE.md §二.6）

逐列实测过，不是推断：

* 仓库根 `plants.csv` 是 `_v9tree/inputs/plants.csv` 的**严格超集**——同样 350 个 `plant_id`、
  同样顺序，32 个共有列的数值差全部 < 1e-9，只多 4 个 v9.1 需要的取水强度列
  （`once_through_withdrawal_*`、`air_withdrawal_*`）。
* v9 的 `pipeline_nodes.csv` 引用的 350 个 `plant_id` **全部存在**于 `plants.csv`。
* `water_availability.csv` 与 `water_nodes.csv` 与 `_v9tree` 逐字节相同（v9.1 已核对）。
* `water_basin_caps.csv` 由指标、预留、`plants.csv` 与 `industry_sources.csv` 生成，
  **不含任何管网信息**，所以直接沿用是正确的。

换句话说：被换掉的是**管网与汇**，被保留的是**源与水**，两者在输入侧没有交叉依赖。

`data/` 是指向仓库根 `data/` 的 junction（流域矢量、封存汇栅格等只读大文件）。

## 四、纪律

1. **本树的运行不得与仓库根 `results/IND_*` 相减。** 那批用的是 v7 管网，可达注入能力只有本树的 62%。
   根目录那四个运行的价值仅限于**接线验证**（工业是否正确进入管网、流域约束与联合目标），
   其**捕集量、注入分布、工业通路份额一律不可引用**。
2. **同样不得与 `_v91tree/` 或任何非 `IND_` 运行相减。** 目标函数分母（5 392 → 8 661 Mt）、
   约束与源群三者同时变了。
3. 本树的两对情景之间（`IND_BASE_t95` ↔ `IND_WA_..._oq_t95`）**可以相减**：同一模型、
